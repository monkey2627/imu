# 录制、回放与验证

本项目目前有三类录制，使用目的不同，不能混用：

| 录制方式 | 用途 | 是否包含视频 |
| --- | --- | --- |
| `run --record` | 推理链路诊断，检查 SolarXR、feature、SMPL 和 Unity/Web 输出 | 否 |
| `production.capture` | 纯 IMU 标定/训练数据采集 | 否，`--video-path` 仅记录路径 |
| Android 联动采集 | 同时保存 IMU、手机视频和会话事件 | 是 |

`production.run --record` 是推理链路诊断录制，保存 SolarXR 输入、两种加速度字段、feature、SMPL 输出、推理延迟和 Unity/Web 诊断数据。Web 页面支持录制、停止、回放和下载 JSONL。

验证顺序：SolarXR 输入 → feature[60] → Python SMPL → Unity Humanoid。只有 Python SMPL 正确而 Avatar 错误时才检查 Unity 重定向。

`run --record` 现在除 `inferenceFrame`（每次推理一行）外，还为**每个 60 Hz 窗口推进**写一行 `windowFrame`（含 tracker 输入和 feature），元数据含 `modelFps/windowFrames/outputIndex/inferEvery/anchored`；`replay_recording` 据此精确重建窗口并与保存的 SMPL 输出逐帧比较。**旧录制（30 Hz、旧模型，元数据没有 `modelFps`）无法回放，会直接报错。** 

replay_recording 用于检查同一录制的一致性。新字段是 FlatBuffers 尾部字段；旧 Server 不生成新字段，当前实时程序会明确报错。离线数值一致性（相对 SparseIMU 基线）见 `07_模型与传感器位置同步_20261019.md`。

## 研究数据采集

不要用推理链路的 `--record` 代替标定数据采集。`production.capture` 是纯 IMU 研究采集，只订阅 SolarXR，保留每次更新的
原始融合姿态、参考系姿态、线性加速度、原始角速度和原始加速度，不写入模型输出：

```bash
python -m production.capture \
  --output recordings/research \
  --subject-id pilot01 \
  --layout pnp5_forearm_shank_pelvis \
  --video-path /path/to/video.mp4 \
  --reference-path /path/to/reference.npz
```

采集前必须先启动 SlimeVR Server，确认 tracker 在线、完成校准，并绑定到正确身体部位。SolarXR 默认地址为 `ws://127.0.0.1:21110`。采集器会先等待五个在线 tracker 与训练布局精确匹配，然后按 D0--D6 动作协议采集，最后默认
保留 30 秒验证窗口。每个会话目录包含 `metadata.json`、`imu_solarxr.jsonl` 和
`events.jsonl`。时间戳是 Python 主机接收时间；不能将其当作传感器采样时间。`--video-path` 当前只是 metadata 字段，`capture.py` 不会控制摄像头或生成视频。

## Android 视频 + IMU 联合采集

联合采集由电脑上的 `capture_server` 负责 SolarXR 与手机协调。Android App 只录制音视频并上传，不连接 SlimeVR，也不运行 FlowHMR。电脑和手机必须连接同一个 WiFi/LAN。

完整顺序是：

1. 启动 SlimeVR Server。
2. 让 IMU tracker 上线，完成校准，并绑定到目标身体部位。
3. 确认 SolarXR 地址 `ws://127.0.0.1:21110` 可访问。
4. 电脑启动 `capture_server`。
5. 手机打开 Android App，授权摄像头、麦克风和通知，输入电脑的 WiFi IPv4 地址及端口。
6. 手机显示 `READY` 后，由电脑统一发送开始命令。
7. 手机开始录制，电脑同时记录 SolarXR 和 session 事件。
8. 电脑发送停止命令，手机停止录制并上传 MP4。
9. 检查 session 目录中的 IMU、视频和元数据文件。

启动服务：

```bash
python -m production.capture_server \
  --host 0.0.0.0 --port 8766 --advertise-host 192.168.1.10 \
  --output recordings/research --subject-id pilot01 \
  --layout pnp5_forearm_shank_pelvis --duration-seconds 120
```

将 `--advertise-host` 换成电脑的 WiFi IPv4 地址；防火墙允许 TCP 8766 入站。服务等待手机连接和 SolarXR tracker 布局匹配后创建 session，触发手机开始录制；手机在 CameraX 实际启动时发短蜂鸣。采集者应同时拍手或跺脚作为可见/可听同步标记。时长结束后电脑发送 stop，手机保存 MP4 并上传。

在 Android Studio 打开 `android_capture_app/`，安装 App，逐项授权摄像头、麦克风及 Android 13+ 通知。输入电脑 IP 与端口 8766，点击 Connect / Reconnect；`READY` 表示手机已在等待。可用 `Start locally` / `Stop` 做本机相机检查。上传失败时保留 App 和本地文件，点击 `Retry upload` 重试。

视频由 Android 手机摄像头单独获得，不是电脑端 `capture.py` 自动生成的。建议手机固定在三脚架或稳定支架上，使用后置摄像头、全身入镜，并保持整个动作过程不变焦。普通手机 RGB 视频即可开始采集；若需要深度或高帧率信息，再使用 RealSense、Azure Kinect、Orbbec 或高帧率相机。手机视频录音用于记录蜂鸣声同步标记，不应当直接当作精确时间基准。

联合 session 保存于 `recordings/research/<session_id>/`，包含 `metadata.json`、`imu_solarxr.jsonl`、`events.jsonl`、`phone_video.mp4` 和 `video_metadata.json`。查询 `/health` 或 `/sessions/<session_id>` 可查看状态。手机临时文件位于 App 私有 `Android/data/org.mobileposer.capture/files/Movies/phone_video.mp4`。

事件中分别保存电脑命令发送时间、SolarXR 首样本主机时间、手机命令接收/录制开始/停止 Unix 与 monotonic 时间。WiFi 远程触发只能启动同一事件，不能保证视频帧与 IMU 采样达到硬件级同步；需用蜂鸣+拍手/跺脚进行后处理对齐，也应考虑手机与电脑时钟偏差。

三种录制功能要区分：`run --record` 记录推理诊断链路；`capture` 记录纯 IMU 研究数据；Android 联动流程记录 IMU、手机视频和事件/session 元数据。`capture.py --video-path` 不会生成或上传视频。
