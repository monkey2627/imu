# 五 IMU 部署抖动诊断（2026-11-11）

结论：旧链路在 Unity 之前就能复现较大的预测不连续。最早的确定性数据流偏差在输入采样调度；
最强的输出不连续证据来自“不断重切窗口、每次只取最后一帧”的在线策略，随后根节点求解把脊柱变化传到骨盆。
Unity 无时间缓冲、收到新姿态就直接应用，会进一步显出跳变。不能据此认为需要先加滤波。

初次诊断只新增只读分析脚本与诊断文档，没有改动训练代码、训练数据或权重。随后按诊断实施的生产修正见文末；未加入低通滤波。

## 2. 四元数、坐标系和加速度

SolarXR 的 quaternion 按 x,y,z,w 解析，`bone_orientation` 同样按 xyzw 转矩阵并归一化。
orientation 经 `SERVER_TO_SMPL=diag(-1,1,-1)` 与前臂固定安装轴转换；
加速度选的是 `reference_adjusted_accel_xyz`，再做相同世界基变换。
适配器忽略其他模型的 `/30` feature，直接读取未经该缩放的 SI 单位 acceleration。
`to_imu6` 计算 `R.T @ (a_world - [0,-9.81,0])`，没有再把线加速度当原始带重力读数。

| 输入统计 | A | B |
|---|---:|---:|
| reference-adjusted 线加速度模长中位数 | 0.334 m/s² | 0.258 m/s² |
| 同上 p99 | 2.546 m/s² | 3.457 m/s² |
| legacy 与 adjusted 加速度向量差 p99 | 3.379 m/s² | 4.147 m/s² |

两字段差异确实很大，不能混用；当前选择路径没有混用。
SlimeVR `TrackerResetsHandler.getFullyReferenceAdjustedAccel` 只施加世界侧校正，
与其方向参考系设计相符，不应将 mounting 的右乘矩阵也当成世界加速度旋转。

另有一个条件性代码缺陷：`calibrator.correct()` 对 orientation 左乘 `headings` 后，
`aligned_accel` 没有同步左乘同一 yaw；右乘安装矩阵不要求旋转世界加速度，但左乘世界 yaw 要求。
若 Python 额外 heading 非 identity，二者将不在同一世界参考中。
原游戏缺少校准快照，不能证明这项在两局中具体造成了多大误差；不能把它排除，也不能把它当作已实测主因。

## 3. gyro 不是空值，也没有单位错成度

`raw_angular_velocity_xyz` 两局均 100% 为 null，但新模型根本不读取该字段。
实际调用原始 `downstream.data.to_imu6`，用 `R[t].T @ R[t+1]` 的旋转向量乘 60，得到 rad/s。
展开后 gyro 模长 p99 A=2.026、B=2.045 rad/s，最大 A=4.056、B=6.189 rad/s；不是全零输入。

问题在时间轴：同一姿态被重复时，相邻旋转差强制为零。展开后零 gyro 比例 A=6.15%、B=6.51%。
例如 A：tick 第 1544 行，t=27.1609066 s，`ticks=2`，前一记录间隔 19.306 ms；
展开后的腰部 gyro 连续为：

```text
[ 0.01685,  0.01511, -0.08917] rad/s
[ 0.00000,  0.00000,  0.00000] rad/s  ← 人为重复帧
[ 0.00027, -0.01954, -0.07079] rad/s
```

训练时是在完整均匀 60 Hz 序列上先算 gyro，再切窗口。
部署却在每次 `predict_window` 中切完最近 480 帧后重新算 gyro：末帧总是 `gyro[-1]=gyro[-2]`，
把真实序列末端的备用处理施加到了每一次在线输出端点。
与“先在完整录制计算 gyro，再切同一个窗口”的对照相比，预测关节角差 p99 A=3.82°、B=4.10°，
最大 A=12.78°、B=16.34°。这是可以单独量出的窗口边界误差。

## 4. 60 Hz 假设与调度：最早的确定性偏离

tick 到达间隔中位 A=17.515 ms、B=17.556 ms，而不是 16.667 ms；p99 分别为 31.445、31.714 ms。
还存在 70/75 个小于 5 ms 的成批写入间隔，最短约 1.06/1.03 ms。
因此不能直接用日志相邻 `t` 取代 gyro 分母：`t` 是记录到达/写入时间，不是各 IMU 的硬件采样时间。
本报告中的时间插值只是一项到达时轴诊断，不是证明已经恢复硬件真实时间。

`production/run.py` 的确定性错误：

```python
repeats = max(0, ticks - len(frames))
# 实际 push 次数 = len(frames) + repeats = max(len(frames), ticks)
frame_index += ticks
since_inference += ticks
```

当积压帧数超过时钟 ticks，实际输入推进比 frame_index/推理调度推进得更多。
子进程仅在内存包裹 `push_observation` 和广播器计数，没有更改生产文件；收取 100 个广播结果：

- `infer_every=6`：真实 push 数减去 `modelInputFrame+1` 从 10 增到 48。
- `infer_every=2`：偏差从 8 增到 24。

随后运行已保存的 `--cadence` 分析入口复验，100 帧内偏差分别达到 52 和 34 帧。
具体数值依赖本机队列调度，但“真实推进与记录计数不一致”可重复出现。

这使输出代表帧、实际模型时轴和调度间隔不再一致。
此外 `InputMux._pump_replay` 只按记录的 t 发一次每个 tick，**不使用保存的 ticks 次数**，
然后又让 FrameClock 在回放机器上重新计算重复数；普通 `--replay` 不等于逐帧确定性复现原窗口。
本次离线重建显式按 `ticks` 展开，避免把这个回放偏差误当模型随机性。

## 5. 输入 backbone 和在线窗口策略：已复现预测不连续

基础字段正确：`imu_data=[5,480,6]`、`freqs=[60,60,60,60,60]`、全有效 mask；
五路经同一冻结 backbone 独立编码，然后按固定顺序拼接为 `[1,30,3840]`，head 输出 `[1,480,138]`。
启动不足 480 帧时左侧重复、mask 全有效，这与训练短片段的右侧零 padding + mask 不同。
下面比较均从拥有至少 480 帧真实历史后开始，已排除启动填充这个因素。

当前在线每次重切最近 480 帧，只取 `head(...)[0,-1]`。stride=6 时 patch 边界不断移动，
attention 的窗口上下文和相对窗口位置也不断改变。head 的线性插值 `align_corners=False` 在最末 8 帧发生端点钳位；
实测最后 8 帧 6D 输出完全相同，最大差为 0。
所以当前输出不是“一个固定上下文内平滑的逐帧插值”，而是“每次重新估计最后一个 patch 的端点”。

统计定义：相邻输出间隔固定为 6 个展开帧（100 ms）；原始模型结果、未加平滑、未加手臂先验；
A 比较 542 个姿态，B 比较 544 个姿态。角度均为 SO(3) 旋转角，以下是 p99，不是精度误差。

| 重建/对照方式 | A 所有关节局部变化 | B 所有关节局部变化 | A 根变化 | B 根变化 |
|---|---:|---:|---:|---:|
| 当前部署：逐次窗口内算 gyro，取末帧 | 12.51° | 13.06° | 7.81° | 10.82° |
| 完整序列算 gyro，仍滑窗取末帧 | 12.59° | 12.97° | 8.48° | 9.97° |
| 到达时间 Slerp/线性重采样后，仍滑窗末帧 | 12.43° | 13.38° | 7.80° | 11.57° |
| 原始输入，训练/验证式 stride240 重叠 6D 平均 | 6.89° | 7.33° | 4.90° | 8.99° |

到达时轴重采样不是滤波；它没有消除预测跳变，故采样错误不能解释全部问题。
stride240 的对照使用相同权重、同一 IMU 输入、同一输出时间网格和同一根节点公式，只改变跨窗读取/融合方法。
但它使用未来上下文，不能直接作为零延迟在线修复，也不是带标签的精度证明。

更直接的反证：比较**同一物理帧**在起点只差 1 帧的两个完整窗口中的预测，去掉真实动作变化这个因素：
所有关节预测差 p99 A=9.71°、B=9.07°，最大 A=27.46°、B=25.67°。
这已经足以说明不断更换窗口本身会引入相当大的不一致。

额外稀疏对照中，即使窗口平移 16 帧、保持 patch 相位，同一时刻的末端附近预测差仍有约 13.54° p99。
因此不能把原因简化为“只需把 infer_every 改成 16”；整个窗口上下文和端点读取也有作用。
窗口内部同一时刻的 1 帧平移差也有约 6–7° p99，不能仅归因于末端补 gyro。

## 6. 权重、eval 和解码

没有发现漏加载 backbone、Dropout 开启、138 当 144、xyzw/wxyz 混用、把 6D 当欧拉角、
或把局部旋转直接当全局旋转的代码证据。
同一输入重复前向的 6D 最大差为 0；这不是模型每次随机抽样。
6D 严格按两个列向量 Gram–Schmidt 解码，23 个孩子放在 SMPL joints 1..23，另行补根。

部署用 float32，特征缓存用 CUDA bf16 编码后存 fp16，再让 head 读取。
同一窗口 fp32 与缓存数值路径的角差 p99 A=2.20°、B=6.59°，最大 A=4.75°、B=11.27°，
说明数值精度差不可声称完全无影响。这是确定性数值敏感性，应作为独立对照项，不能用它解释同一输入的随机抖动。

完整滑窗对照中，切回 bf16→fp16 缓存特征数值路径后，局部相邻变化 p99 仍为 A=12.55°、B=12.93°，
根变化 p99 仍为 A=8.70°、B=9.63°；没有消除跳变。因此“改回训练精度”也不是单独充分的修复。

## 7. 根姿态/平移

实际补根是 `R_root = measured_waist @ predicted_local_spine1.T`，并非读取真实骨盆或网络预测根。
两局 FK 重建的 joint3 全局方向与测量腰部最大矩阵误差均约 4.17e-7，公式本身一致。

但腰部相邻输出变化中位 A=0.57°、B=0.50°，求出的根变化中位 A=2.12°、B=2.14°；
根 p99 为 7.81°/10.82°，预测 spine1 局部变化 p99 为 7.31°/10.52°。
该公式会把预测 spine1 的逆向变化传到骨盆，即使测量腰部相对稳定。
当前重建的左右大腿全局变化 p99：A=19.61°/16.39°，B=27.53°/20.12°。
仅在诊断中固定根，大腿变化有所下降，但并不改善所有骨段，因此根是传播/放大环节，不是唯一来源；不能直接把根固定作为正确修复。

Python 协议不发送根平移；Unity `LateUpdate` 也不从模型设置位置。
可选 `AutoGroundRootFromAvatar` 会根据最低骨点调整人物高度，若开启会将旋转跳变变成上下位移。
源码默认 `groundAvatar=false`，但两份录制不保存当局 UI 选项或人物 world position，
不能据此断定用户当时是否开启贴地，也不能证明所有视觉平移都来自它。

## 8. 推理、广播、Unity 应用

离线逐窗编码+head，在本机 RTX 4090 上预热后中位约 8.9/8.8 ms，p99 约 12.0/11.7 ms。
真实生产入口通过现有回放和 WebSocket 收取 100 帧，去掉最初 4 帧，用 perf_counter 测量：

| 配置 | 广播到达中位 | p90 | p99 | 推理耗时中位 |
|---|---:|---:|---:|---:|
| infer_every=6（目标10 Hz） | 104.18 ms | 112.69 ms | 124.94 ms | 15.04 ms |
| infer_every=2（目标30 Hz） | 36.63 ms | 58.02 ms | 69.69 ms | 15.94 ms |

这些是本次本机回放数据，不能冒充两局原始推理耗时；原日志没有这一字段。
GPU 前向不是持续超时到几十/几百毫秒的唯一解释；输入调度仍导致不均匀输出。

`ProcessMessage` 替换 latestJoints；`LateUpdate` 每渲染帧直接使用最后一份数组，并直接赋值 `bones[i].rotation`。
没有按 source frame/time 的插值队列，没有插值播放时钟；同一姿态保持若干画面帧后直接跳至下一姿态。
这会让已有预测跳变和到达不均匀更明显，但不能解释前面离线计算已测出的关节不连续。
Unity 是正确地先按 SMPL parent 链得到全局方向，再做 bind pose 重定向。
coach 录制脚本临时写骨架后有 finally 恢复；没有证据仅凭它断定教练姿态在画面上交替覆盖预测。

手臂先验另测：局部相邻变化最大值 A 从 55.47° 增至 70.23°，B 从 45.67° 增至 71.23°；
它只作用肩肘，不能解释全身抖动，但排查原始模型时应单独关闭。
原两局没有保存该选项，不能证明当时是否启用。

## 后续仍需处理什么

1. 先统一单调采样时轴和真实 push 计数，保留每路新鲜度，修正积压/丢弃/重复的明确规则；
   回放应按保存的 ticks 和校准快照确定性推进，而不是再跑一套到达时钟。
2. gyro 在统一采样序列上连续计算后再组窗，避免每窗末端复制旧 gyro；
   训练是前向差分，严格重用需要至少一个采样帧的未来旋转，应显式声明这帧延迟。
   同时核对非 identity 世界 yaw 校准时加速度是否同步变换。
3. 用同一录制验证固定 patch/窗口调度及有明确延迟的跨窗读取/融合，比较同一物理帧的一致性、根与肢体变化。
   不能只改 infer_every，也不能把离线 240 stride 重叠融合不加区分地用于低延迟交互。
4. 根姿态保留独立策略与诊断；避免将未经验证的 spine1 抖动直接当作可信骨盆变化。
   同时记录实际 model output、选项、根位置、推理代表帧、到达时间和校准快照，补齐原游戏不可追溯的信息。
5. 数据流与 Unity 插值修复后，仍需独立评估模型跨窗不一致。当前离线录制没有网络预测标签，不能证明原始模型预测精确；
   **没有加入模型输出低通滤波**，也没有证据要求重新训练。

## 已实施修正（2026-11-11）

- `production.run` 以单调时间戳将 SolarXR 快照重采样到固定 60 Hz：方向用 quaternion SLERP、加速度线性插值；使用每个更新各自的到达时间，按实际调度帧数推进窗口。任一必需 tracker 离线或超过 150 ms 未更新时暂停推理，不再无限沿用旧样本。
- 传感器校准的 world-yaw 同步应用到 IMU orientation 和 acceleration，再执行模型预处理，避免非 identity heading 下两个输入通道落入不同世界坐标系。
- 输入录制现在写每一个实际进入模型的均匀 60 Hz 帧。Replay 按 `ticks` 在相同 60 Hz 时间网格展开，并保留完整队列，不再按录制写入时间/本机 FrameClock 猜样本重复数。
- IMUDINO 窗口末端有 8 帧被 head 的 `align_corners=False` 插值 clamp 成相同预测。在线输出改取窗口 index 471（零基），并额外读取 1 帧真实样本计算末端 gyro；pelvis root 与同一目标时刻的腰部方向配对，`modelLagFrames=9` 使校准锚定也选同一帧。
- Unity 仅对 `waist_imudino_fiveimu` 缓冲至少 4 个 60 Hz 帧（若 Python 输出 stride 更大，则自动按 `inferEvery + 1` 加深缓冲），并基于高精度单调计时器持续推进显示时刻，用 Python 输出代表帧号做四元数 SLERP；其他模型保持立即应用。这是传输/渲染时间插值，不是模型姿态低通滤波。
- 诊断脚本更新为比较 IMUDINO 的 index 471 在线输出。

两份旧录制可验证离线重采样与新的输出帧索引/根时刻；Unity 缓冲及目标游戏电脑上的 SlimeVR 到达抖动仍需实测。模型本身仍会跨窗变化，不能据此承诺完全无抖动。

## 2026-11-12 复核：基于新日志 235722（含 prediction）

脚本（只读）：`analysis.imudino_jitter_stages`、`analysis.imudino_readout_sweep`、`analysis.imudino_adapter_replay_check`。
所有角度为 SO(3) 测地角，"2 帧步长"指相邻输出代表帧相差 2 帧的成对比较。

0. **可复现性**：用 tick 行（加速度须经 `identity_heading.apply` 转到 SMPL 基 `diag(-1,1,-1)`）重放 1611 个完整窗口，
   与录制 `rawLocalQuaternions` 差 p99 0.03°、max 0.04°；CPU 与 GPU 结果相同。tick 与 prediction 的帧号偏移恒为 9812，
   由根求解反推的腰部帧 96% 恰为 `newest-9`。→ `FiveIMUAdapter.infer()` 的输出就是该窗口模型输出，录制可信。
   （之前未做基变换时出现的 p50 2.3° 不一致是分析脚本错误，不是程序问题。）
1. **输入**：五路齐全、校准快照恒为 identity；比力模长中位 9.77–9.94 m/s²，gyro p99 0.7–5.9 rad/s，量纲与训练约定一致；
   精确重复帧 5–10%（源端未更新，插值后为零步），会产生零 gyro 片段。输入每帧变化远小于输出跳变。
2. **单窗口内输出是平滑的**：同一窗口在 index 471 处 2 帧变化 p99 左髋 3.5°、左膝 4.9°、肘 3.3–4.5°。
3. **跳变来自"每次换窗口只读末端"**：同一物理帧在相差 2 帧的两个窗口中的预测差 p99 左髋 14.3°、左膝 18.1°、肘 12.6°，
   与线上相邻输出变化（左髋 16.8°、左膝 20.9°、肘 13.1°）几乎相等。即线上抖动 ≈ 窗口放置方差，而非真实运动。
   训练/验证从不以这种方式读输出（stride 240 固定窗口 + 重叠平均）；同一输入按 stride240 拼接时 2 帧变化 p99 仅 1.5–4°。
   这是最先偏离训练/验证约定的阶段。模型对输入也很敏感（线加速度置零 → 输出变化 p99 15–25°），但这不是可在部署端修的偏差。
4. **根节点**：全局 spine1 = 测量腰部，2 帧变化 p99 1.39°；根 p99 8.05° 完全来自预测 spine1 局部抖动的反向传播。
   令根=腰部只是把抖动移到 spine2/3，不能消除。anchor 使 Unity 中膝/肘全局方向跟随传感器（p99 3–5°，右肘 12°），
   但髋/肩全局仍 p99 17–22°。注意：raw 与 unity 四元数**并不相同**——anchor 改写膝/肘局部，手臂先验改写肩。
5. **时序**：Python 发帧间隔中位 33.9 ms、p99 45.6 ms，代表帧步长 1/2/3，与帧时钟无累计漂移（−0.21 帧）。
   Unity `LateUpdate` 每到一包就把播放时钟重锚到 `latest-4+elapsed*60`，模拟 60/144 Hz 渲染时播放速度 p1–p99 为 0.45–1.7× / 0–2.4×。
   这是次要的时间扭曲（相当于 ≤1 帧位置误差），不能解释 15–20° 跳变；本次未改。

### 修改：同帧多窗口集成读出（不训练、不滤波、不增加推理）

`FiveIMUAdapter.infer()` 把每个已算窗口在 index ∈ [480−lag, 471] 的 6D 预测按**绝对帧号**累积；
输出帧 `newest−lag` 取所有曾以 index ≤ 471 覆盖该帧的窗口的 6D 平均，再按验证拼接同样方式正交化。
不混合相邻帧；lag=9 时与旧行为逐位一致。lag 由 `MOTION_RECOVER_IMUDINO_LAG` 设定（9–48，默认 15），
`model_lag_frames` 同步读取，因此 anchor、arm prior 的测量帧、diagnostics 与 Unity 的代表帧一起变化。

按录制的真实推理节拍重放（1611 帧）：

| lag | 延迟 | 每帧窗口数 | 局部 2 帧 p50/p99 | 全局 2 帧 p50/p99 | 左膝/左髋局部 p99 | 与 stride240 拼接差 p50/p90 |
|---:|---:|---:|---:|---:|---:|---:|
| 9（旧） | 150 ms | 1 | 2.24 / 12.74° | 2.57 / 16.52° | 20.9 / 16.8° | 3.26 / 8.43° |
| 15（默认） | 250 ms | 4 | 0.67 / 3.90° | 0.89 / 5.34° | 6.2 / 4.6° | 2.70 / 7.10° |
| 23 | 383 ms | 8 | 0.45 / 2.97° | 0.67 / 4.14° | 4.6 / 3.2° | 2.39 / 6.53° |

与验证式拼接的距离同时下降，说明这是减小窗口放置方差而非把输出抹平。代价是额外 100 ms 延迟（lag 15）。
`checkpoints/.../manifest.json` 中的 `online_lag_frames: 9` 未改（不动 checkpoint 目录），以运行时配置为准。

未验证：实机 SlimeVR + Unity 的主观观感与延迟体感；其他录制/动作；lag 改变后校准 anchor 的时间对齐只做了代码核对。
