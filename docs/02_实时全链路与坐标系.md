# 实时全链路与坐标系

## 数据链路

```text
IMU/AHRS
→ Tracker UDP
→ SlimeVR Server reset/reference chain
→ SolarXR ws://127.0.0.1:21110
→ Python Server→SMPL 坐标转换
→ MobilePose feature[60] / 91 帧（60 Hz）窗口
→ SMPL 24 local rotations
→ Web/Unity ws://127.0.0.1:21200
```

## SolarXR 字段

| 字段 | 含义 | 当前用途 |
|---|---|---|
| `rotation` | 固件融合姿态，尚未应用 SlimeVR reference reset | 诊断和录制 |
| `rotationReferenceAdjusted` | 应用 SlimeVR 安装/参考修正后的姿态 | MobilePose 方向输入 |
| `linearAcceleration` | 使用原始融合旋转得到的旧世界线性加速度 | 录制兼容，不用于当前实时主线 |
| `referenceAdjustedLinearAcceleration` | 应用参考旋转链世界侧修正后的线性加速度 | 当前实时加速度输入 |

新增加速度字段会应用 Stay Aligned、gyro/mount/yaw/constraint/drift 等世界侧修正，不把 mounting orientation、attachment 或 T-pose 等局部骨骼轴修正误用于世界加速度。

每个 Tracker 有独立修正状态。校准后矩阵通常固定；若启用 Stay Aligned、漂移补偿或 reset smoothing，矩阵可随时间变化。无论矩阵是否变化，输出都对每帧当前旋转和加速度重新计算。

## 模型输入

五个加速度各 3 维、五个方向矩阵各 9 维（**加速度在前**，与训练数据 `data.py` 一致，也是 `infer.build_feature` 的实际顺序）：

```text
feature[60] = acceleration[15] / 30 + orientation[45]      # 传感器顺序 lw rw ls rs pelvis
```

方向和加速度都执行 Server→SMPL 基变换 `diag(-1, 1, -1)`；前臂输入还使用固定 ±90° z 轴变换（SlimeVR 骨骼轴 → SMPL 骨骼轴的约定，与传感器位置无关，保持不变）。加速度按训练约定 `/30`。单位在缩放前为 `m/s²`。

启动直立采集只用于用同一帧 feature 填充 91 帧历史窗口，不改变长期预测能力。

## 帧率、窗口与推理节拍

模型按 60 fps 数据训练。窗口按固定 60 Hz 推进：每个 60 Hz 节拍用最新的 SolarXR 样本推入一帧（漏掉的节拍用最新样本补齐，保证时间轴均匀；停顿超过 4 个节拍则重新对齐时钟）。网络默认每 2 帧推理一次（`--infer-every 2`，30 poses/s），也可 `--infer-every 1`（60 poses/s）。在线窗口 = 过去 80 + 未来 10 帧（对应 MobilePose 的 `win46`：30 fps 下 40 + 5 帧）。

## 输出与延迟

MobilePose 输出 SMPL 24 个局部旋转矩阵，再转换为 Unity 四元数。模型窗口造成 10 帧 @60 Hz 的输出滞后，约 167 ms，另有采集、推理、WebSocket 和 Unity 渲染延迟。输出里没有足接触（新基线没有接触头），`footContact` 字段不再发送，Unity 接收端把它当作可选字段。

Unity 的 tracker anchor、地面约束、IK 和关节限位属于下游后处理，不应反向当成模型输入真值。
